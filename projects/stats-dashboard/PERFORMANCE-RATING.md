# Performance-impact rating criteria (v1.5)

Ratings for every **loaded extension** and **loaded tool** on a 1–5 scale:
**1 = lowest cost, 5 = relatively high performance hit**.

The rating is a *global* (all sessions, all processes) assessment based on
**measured data**, not a static opinion:

```
rating = clamp(1, 5, round(0.5·duration + 0.3·frequency + 0.2·static))
```

Each factor is banded 1–5 from the measured value (value ≥ edge ⇒ one band up):

| factor      | 1            | 2            | 3            | 4            | 5             |
| ----------- | ------------ | ------------ | ------------ | ------------ | ------------- |
| duration¹   | no data / <50ms | <200ms     | <1 s         | <10 s        | ≥10 s         |
| frequency²  | <10 runs     | <100 runs    | <1 k runs    | <10 k runs   | ≥10 k runs    |
| static³     | <2 KB        | <8 KB        | <32 KB / unknown | <102 KB   | ≥102 KB       |

¹ **duration** — measured average wall-clock duration per call, in ms, from
   `tool_execution_end.durationMs` (fallback: start/end wall clock).
   Only **tools** have measured durations; extensions always score band 1 here
   (no per-call measurement exists for them).
² **frequency** — global run count from the usage store
   (`usage-stats.json`), i.e. how often the tool/extension actually executes.
³ **static** — size of the implementation (tools:
   `dist/core/tools/<name>.js`; extensions: the extension source file) in
   bytes; **unknown size (dynamic/MCP tools, unreadable files) scores the
   neutral band 3**. For **extensions only**, the static factor is
   `max(size-band, subscription-band)`, where subscription-band is banded from
   the number of `pi.on(...)` event subscriptions:

   | 1        | 2        | 3       | 4       | 5     |
   | -------- | -------- | ------- | ------- | ----- |
   | 0–1 subs | 2–3 subs | 4–5 subs| 6–9 subs| ≥10 subs |

   Extensions that render per TUI frame (source contains `ui.custom(`,
   `showOverlay(` or `registerComponent(`) get **+1** to the static factor
   (capped at 5) — per-frame rendering is a real, recurring cost.

## Why these weights

- **duration (0.5)** — the dominant, directly user-visible cost: a tool that
  takes seconds blocks the agent's turn.
- **frequency (0.3)** — an expensive operation repeated thousands of times
  compounds; a slow tool that runs once per session matters less.
- **static (0.2)** — memory/import cost and per-event handler overhead.
  Small compared to runtime behaviour, but per-frame TUI work and many
  subscriptions are a steady tax, hence the extension-specific factors.

## Where the data comes from

| source | path | written by |
| ------ | ---- | ---------- |
| tool durations | `~/.pi/agent/perf-stats.json` | `stats.ts` on every `tool_execution_end` (env override `PI_STATS_PERF_FILE`) |
| run counts | `~/.pi/agent/usage-stats.json` | `stats.ts` + instrumented extensions (env override `PI_STATS_USAGE_FILE`) |
| static metrics | read live from source files (30 s cache) | — |

Durations are only recorded when a valid number is available
(`durationMs` from pi, else wall clock ≥ 1 ms). Invalid/missing values are
**not** recorded — no 0 ms pollution.

## Where the rating is visible

1. **Live, in `/stats`** — the RIGHT column has a `perf rating (1 cheap · 5
   costly)` section, sorted by rating (descending), each row
   `name  N [· avg/call] · M runs`, recomputed from the stores on every
   dashboard refresh.
2. **File deliverable** — `perf/perf-ratings.json`, generated by
   `node perf/rate.mjs` from the same stores and the exact same
   `rateItem()` implementation (the script is the reference for these
   criteria).

## Limitations (kept honest)

- Extension durations are not measured (no per-call hooks exist), so
  extension ratings are static + frequency driven. A slow extension that runs
  rarely may be underrated; a fast one with 10 subscriptions may be
  overrated.
- `durationMs` from pi is wall-clock, not CPU time — it includes waits (e.g.
  network in `bash`). That is the honest measure of user-perceived cost.
- The rating is an *impact* score, not a quality judgement: a 5 means
  "costly to run", not "bad extension".
- MCP/dynamic tools have unknown implementation size (neutral band 3) until
  their durations accumulate.
